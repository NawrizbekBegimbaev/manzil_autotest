## BUG-035 (→ MNZL-275) — Гонка state-transition заказа (cancel / enter-1c): 500 вместо 409 (dev)

- **Краткое описание:** Две параллельные смены состояния одного заказа: проигравший периодически получает 500 вместо 409. Подтверждено на cancel (SELECTED) и enter-1c (IN_TRANSIT).
- **Полное описание:** `POST …/{id}/cancel` и `POST …/{id}/enter-1c` не сериализуют доступ к строке заказа пессимистичной блокировкой. Winner-select тот же конфликт решает через `findByIdForUpdate` (пессимистичный лок) + `@Version` и корректно отдаёт 409. Эти пути читают через `findByIdAndShipperCompanyId` (без лока) и полагаются только на `Order.@Version`; при истинном конфликте версий исключение не всегда мапится глобальным хендлером в 409 `error.concurrent-modification` и вываливается как 500 `INTERNAL_SERVER_ERROR`. Для enter-1c при корректном маппинге виден 409 `CONFLICT` «数据已被另一操作修改». Целостность не нарушена (двойного перехода нет), но контракт ошибки нарушен.
- **Воспроизведение:** заказ → SELECTED (cancel) / IN_TRANSIT (enter-1c); одновременно два одинаковых POST; повторить ~3–6 раз (недетерминированно, ~1/3–1/2 гонок → 500).
- **Сервер (факт):** `{"code":"INTERNAL_SERVER_ERROR","status":500,"detail":"服务器内部错误","instance":"/api/v1/shipper/orders/{id}/cancel|enter-1c"}`.
- **Ожидается:** `409` (проигравший) — как в winner-select.
- **Фикс (проверено по исходникам):** `bid`/`select` уже берут `findByIdForUpdate` (пессимистичный лок заказа) — их гонки чистые (0×500, подтверждено автотестами офферов). `cancel`/`enter-1c` читают без `ForUpdate` — **взять тот же `findByIdForUpdate`** (либо гарантировать, что `@Version`-конфликт долетает до `GlobalExceptionHandler` как `OptimisticLockingFailureException`).
- **Кейсы/тесты:** API-SHP-080 · `test_cancel_race_080`; API-SHP-116 · `test_enter1c_race_116` (оба `xfail(strict=True)`).

## BUG-036 (→ MNZL-276) (low) — Непоследовательное сокрытие кросс-тенантных ресурсов: 403 вместо 404 (dev)

- **Краткое описание:** Чужой склад при PATCH/DELETE → 403 (раскрывает существование), тогда как заказы/офферы/сотрудники при кросс-тенанте → 404 (скрывают).
- **Источник (manzil-core):** `WarehouseService.ownedWarehouse` — `warehouseRepo.findById(id).orElseThrow(notFound)` затем `if (!companyId.equals(warehouse.getShipperCompanyId())) throw forbidden("error.forbidden")`. Тот же паттерн — `OrderDriverService` (привязка водителей). Доминирующая конвенция (23 места) — `findByIdAndShipperCompanyId(...).orElseThrow(notFound(...))` → 404, существование не раскрывается.
- **Влияние:** low — UUID v4 неперебираемы, доступ закрыт; утечка факта существования, не обход авторизации.
- **Решение за продуктом:** унифицировать на 404 (BOLA-safe) либо зафиксировать отклонение правилом в PROJECT_REFERENCE.
- **Кейсы/тесты:** API-SHP-157/161 · `test_warehouse_update_tenancy_157` / `..._delete_tenancy_161` (проверяют факт 403, ссылка → BUG-036 / MNZL-276).

## BUG-028 ✅ — Сообщения об ошибках в приложении склада на английском (не локализованы)

- **Краткое описание:** Приложение склада (узбекский UI) показывает ошибки на английском вместо узбекского.
- **Полное описание:** Тексты ошибок захардкожены/не локализованы. Обнаружено на экране входа (3 случая):
  - wrong-app (чужая роль): «Access denied» (сервер: 403 error.wrong-app);
  - неверный пароль: «Phone or password is incorrect» (сервер: 401 error.invalid-credentials);
  - лимит попыток: «Too many requests» (сервер: 429 после 5 неудач).
  Приложение не показывает локализованное сообщение сервера. Прочий UI локализуется нормально (напр. пустое состояние «Пока нет заказов») — пробел точечно в сообщениях авторизации. Из той же семьи i18n-дефектов, что BUG-019/020/027.
- **Шаги воспроизведения:**
  1. Открыть приложение склада (узбекский UI).
  2. а) Ввести телефон чужой роли (напр. 900000003) → «Kirish» → «Access denied».
     б) Ввести валидный телефон + неверный пароль → «Kirish» → «Phone or password is incorrect».
     в) Повторить неверный пароль 5 раз → «Too many requests».
- **Ожидаемый результат:** Локализованные (узбекские) сообщения об ошибках.
- **Фактический результат:** Английские тексты «Access denied» / «Phone or password is incorrect». (Функционально отказы входа корректны.)
- **Приоритет:** P4 (i18n; функционально работает).
- **Сторона:** 📱 Mobile Frontend (приложение склада — локализовать сообщения об ошибках).
- **Доказательство:** ✅ проверено вручную 2026-07-17 (пользователь): «Access denied» (wrong-app) и «Phone or password is incorrect» (неверный пароль).

## BUG-029 ✅ — Приложение перевозчика: wrong-app показан как «Непредвиденная ошибка»

- **Краткое описание:** При входе чужой ролью в приложение перевозчика показывается общая ошибка «Непредвиденная ошибка. Попробуйте снова» вместо понятного сообщения «приложение не для вашей роли».
- **Полное описание:** Приложение перевозчика не распознаёт осмысленные ответы сервера и валит их в generic-ошибку «Непредвиденная ошибка. Попробуйте снова». Подтверждено на двух случаях: 403 error.wrong-app (чужая роль) и 429 rate-limit (5 неудач входа). Пользователь не понимает причину (выглядит как поломка). (В отличие от приложения склада — BUG-028 — тут текст русский, но бессмысленно-общий.)
- **Шаги воспроизведения:**
  1. Открыть приложение перевозчика.
  2. а) Ввести телефон чужой роли (склад 900000004) → «Войти» → «Непредвиденная ошибка».
     б) Ввести валидный телефон + неверный пароль 5 раз → «Непредвиденная ошибка» (вместо «слишком много попыток»).
- **Ожидаемый результат:** Понятные сообщения: «Это приложение не для вашей роли» (wrong-app) и «Слишком много попыток, попробуйте позже» (429).
- **Фактический результат:** Оба случая → «Непредвиденная ошибка. Попробуйте снова» (generic); вход не выполнен.
- **Приоритет:** P3 (вводит в заблуждение — выглядит как сбой; особенно для 429 пользователь не понимает, что нужно подождать).
- **Сторона:** 📱 Mobile Frontend (приложение перевозчика — обработать 403 error.wrong-app отдельным сообщением).
- **Доказательство:** ✅ проверено вручную 2026-07-17 (пользователь): показано «Непредвиденная ошибка. Попробуйте снова».

## BUG-030 ✅ — Универсальное неверное сообщение на любую ошибку назначения водителя

- **Краткое описание:** Приложение перевозчика на любую ошибку назначения водителя показывает один и тот же текст «Заказ не готов к назначению водителя или превышен лимит водителей», не соответствующий реальной причине.
- **Полное описание:** Сообщение — универсальная заглушка, лепит две причины в одну и появляется в разных ситуациях, часто ни к одной не подходя:
  - неполный комплект (1 из 2) — реально «не хватает водителей» (drivers-incomplete), а не «не готов к назначению» и не «превышен лимит»;
  - выбран водитель, уже назначенный на этот заказ (см. BUG-031) — реально «водитель уже прикреплён»;
  - заказ уже с полным комплектом (2/2) — реально «лимит достигнут».
  Функционально назначение/замена/старт при корректных действиях работают; проблема именно в тексте — пользователь не понимает, что не так.
- **Шаги воспроизведения:**
  1. Заказ с `driversCount=2`. Спровоцировать любую ошибку назначения: назначить 1 из 2 / выбрать уже назначенного водителя / добавить сверх лимита.
- **Ожидаемый результат:** Сообщение, соответствующее конкретной причине (не хватает водителей / водитель уже на заказе / лимит достигнут).
- **Фактический результат:** Во всех случаях — «Заказ не готов к назначению водителя или превышен лимит водителей».
- **Приоритет:** P4 (текст/UX; функционально корректные действия работают).
- **Сторона:** 📱 Mobile Frontend (приложение перевозчика — показывать конкретную ошибку сервера вместо универсальной заглушки).
- **Доказательство:** ✅ проверено 2026-07-20 (пользователь, скриншоты): одинаковое сообщение при неполном комплекте и при выборе уже назначенного водителя. Бэкенд назначение 2/2 принимает (API-тест → 200).

## BUG-031 ✅ — При замене водителя в списке кандидатов показан водитель, уже назначенный на этот же заказ

- **Краткое описание:** На заказе с 2 водителями при замене одного из них экран «Назначить водителя» показывает как кандидата **второго водителя, который уже назначен на этот же заказ** — выбрать его бессмысленно.
- **Полное описание:** Заказ NAMA-00024 (В работе, 2 водителя: CR049 Test и jbfbcf). При нажатии «Заменить» (карандаш) у одного водителя список кандидатов содержит jbfbcf — второго, уже прикреплённого к ЭТОМУ заказу. Если его выбрать — сервер вернёт «водитель уже прикреплён» (error.order.driver-already-attached). Список кандидатов замены должен исключать водителей, уже назначенных на этот заказ (кроме заменяемого). По API `available-drivers` включает водителей текущего заказа (для показа текущего) — приложение должно отфильтровать остальных при замене.
- **Шаги воспроизведения:**
  1. Заказ с `driversCount=2`, оба водителя назначены.
  2. Нажать «Заменить» (карандаш) у одного водителя.
  3. Посмотреть список кандидатов на экране «Назначить водителя».
- **Ожидаемый результат:** В списке — свободные водители + текущий (заменяемый); второй водитель этого же заказа исключён.
- **Фактический результат:** В списке присутствует второй водитель, уже назначенный на этот заказ (нелогичный/недопустимый выбор).
- **Приоритет:** P3 (сбивает с толку; выбор приведёт к ошибке).
- **Сторона:** 📱 Mobile Frontend (приложение перевозчика — фильтровать из кандидатов замены водителей, уже прикреплённых к заказу).
- **Доказательство:** ✅ проверено 2026-07-20 (пользователь, скриншоты): NAMA-00024, при замене показан jbfbcf, уже назначенный на этот заказ. Подтверждается контрактом `available-drivers` (включает водителей текущего заказа).

## BUG-032 ✅ — Уведомления перевозчика на китайском (не локализованы)

- **Краткое описание:** В приложении перевозчика содержимое уведомлений отображается на китайском независимо от языка приложения.
- **Полное описание:** Экран уведомлений работает (список открывается, тап помечает прочитанным, бейдж уменьшается), но текст уведомлений — на китайском (staging China-first). Пользователь, не владеющий китайским, не может прочитать свои уведомления. Вероятно, уведомления генерируются на дефолтном языке сервера, а не на языке пользователя/приложения.
- **Шаги воспроизведения:**
  1. Войти перевозчиком, открыть «Bildirishnomalar»/Уведомления.
  2. Посмотреть текст уведомлений при языке приложения ru/uz.
- **Ожидаемый результат:** Уведомления на языке приложения/пользователя.
- **Фактический результат:** Текст уведомлений на китайском.
- **Приоритет:** P3 (i18n; уведомления нечитаемы для не-китайских пользователей).
- **Сторона:** 🔧 Backend (осн., генерировать уведомления на языке пользователя) / 📱 Mobile (передавать язык, напр. Accept-Language).
- **Доказательство:** ✅ проверено 2026-07-20 (пользователь): содержимое уведомлений на китайском при русском/узбекском UI.

## BUG-033 ✅ — Нет подтверждения при выходе из аккаунта (приложение перевозчика)

- **Краткое описание:** «Chiqish» (Выход) выполняет выход сразу по тапу, без диалога подтверждения.
- **Полное описание:** При нажатии «Выход» приложение перевозчика немедленно разлогинивает без запроса подтверждения. Нужен диалог «Вы точно хотите выйти из аккаунта?» (Да/Отмена), чтобы избежать случайного выхода.
- **Шаги воспроизведения:**
  1. Войти перевозчиком, открыть профиль.
  2. Нажать «Chiqish» (Выход).
- **Ожидаемый результат:** Диалог подтверждения «Вы точно хотите выйти из аккаунта?» → выход только после подтверждения.
- **Фактический результат:** Мгновенный выход без подтверждения.
- **Приоритет:** P4 (UX-улучшение; защита от случайного выхода).
- **Сторона:** 📱 Mobile Frontend (приложение перевозчика — добавить диалог подтверждения выхода).
- **Доказательство:** ✅ проверено 2026-07-20 (пользователь): выход происходит сразу по тапу, без предупреждения.

## BUG-034 ✅ — Диалоги/формы приложения перевозчика на узбекском при русском UI

- **Краткое описание:** В приложении перевозчика (язык — русский) ряд диалогов и форм показан на узбекском — не следуют выбранному языку.
- **Полное описание:** Основной UI на русском («Автопарк», «Добавить водителя», «Поиск по ФИО…»), но всплывающие диалоги/формы захардкожены на узбекском:
  - диалог удаления водителя: «Haydovchini o'chirish», «Ushbu haydovchini o'chirilsinmi?», «Bekor qil…» / «O'chirish»;
  - форма добавления водителя: «Yangi haydovchi», «To'liq ism», «Telefon raqam», «ID karta raqami», «Bekor qilish» / «Saqlash».
  Смешение языков — диалоги/формы не переключаются на язык приложения.
- **Шаги воспроизведения:**
  1. Язык приложения — русский. Раздел «Автопарк».
  2. а) Нажать удалить (корзина) у водителя. б) Нажать «Добавить водителя».
- **Ожидаемый результат:** Диалоги и формы на языке приложения (русский).
- **Фактический результат:** Диалог удаления и форма добавления — на узбекском при русском остальном UI.
- **Приоритет:** P3 (i18n; смешение языков).
- **Сторона:** 📱 Mobile Frontend (приложение перевозчика — локализовать диалоги и формы автопарка).
- **Доказательство:** ✅ проверено 2026-07-20 (пользователь, скриншоты): UI русский, диалог удаления и форма добавления водителя — узбекские.
