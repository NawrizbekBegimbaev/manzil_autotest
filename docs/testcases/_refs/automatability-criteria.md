# Критерий автоматизируемости тест-кейсов Manzil

Задача: в каждом JSON-файле оставить ТОЛЬКО кейсы, которые можно автоматизировать
детерминированным скриптом (API: requests/httpx; Web: Playwright; Mobile: Maestro),
а НЕавтоматизируемые вынести в архив. Решение — по существу кейса (screen/scenario/
steps/expected/comment), НЕ по одному тегу.

## АВТОМАТИЗИРУЕМО (оставить) — если скрипт может ВОСПРОИЗВЕСТИ и ДЕТЕРМИНИРОВАННО проверить

- **API**: HTTP-запрос → проверка HTTP-кода, `ProblemDetail.code`, полей тела, заголовков,
  пагинации, идемпотентности, гонок (через параллельные запросы). Практически ВСЕ API-кейсы.
- **Web (Playwright)**: навигация, редиректы/гварды по ролям, заполнение формы + текст ошибки
  валидации (assert текст присутствует), CRUD-сохранение → текст тоста + изменение списка,
  фильтры/поиск/вкладки → параметры URL, чипы активных фильтров (появились/сняты), сброс
  страницы при смене фильтра, количество строк в таблице, видимость/скрытие элемента по роли/
  capability, enabled/disabled кнопки, наличие/отсутствие пункта меню, открытие/закрытие диалога,
  предзаполнение полей, сохранение значения после reload, значение в localStorage, факт смены
  темы через измеримый признак (напр. `body` background rgb / `data-mui-color-scheme`), факт
  смены языка через КОНКРЕТНЫЕ строки-подписи.
- **Mobile (Maestro)**: запуск, логин, тап-флоу, `assertVisible` по подписям, создание заявки,
  переключение вкладок, статусы через API-seed.

Правило пограничных: если в кейсе есть ХОТЬ ОДНА детерминированная проверка — считать
автоматизируемым (напр. «тёмная тема → фон тёмный rgb» — авто; «язык переключился → появилась
строка X» — авто).

## НЕ АВТОМАТИЗИРУЕМО (в архив) — требует человеческого суждения или нестабильно

- **Чистый визуал/вёрстка**: «вёрстка не съезжает», «текст не обрезан/не наезжает», «форма прыгает
  при клавиатуре» (как визуальный дефект), «скелетон выглядит правильно», выравнивание, отступы.
- **Корректность цвета/стиля как смысла**: «чип оранжевый/правильного цвета», «статус читаемого
  цвета», «тёмная тема выглядит хорошо» (эстетика). NB: факт применения темы через rgb — авто.
- **Корректность локализации (качество перевода)**: «перевод корректный/естественный/грамотный»,
  «нет опечаток» — нужен человек, читающий язык. NB: факт «подпись сменилась на строку X» — авто.
- **Доступность, требующая человека**: объявления скринридера, «фокус визуально виден»,
  «озвучивается корректно». NB: программный аудит axe/наличие aria-атрибута — авто.
- **Адаптив как эстетика**: «на мобильном вьюпорте выглядит хорошо/удобно» (без измеримого признака).
- **Кейсы без детерминированного ожидания**: expected по сути = «(проверить на устройстве)»,
  «убедиться визуально», «оценить удобство», без конкретного assert.
- **Требующие реального устройства/кросс-браузерного визуала/печати/камеры**.

## Практические подсказки по тегам comment (НЕ абсолютны — решать по сути)
- `a11y`, `responsive` — ЧАЩЕ в архив, но оставить, если есть программная проверка (aria/атрибут/размер).
- `i18n` — оставить, если проверяется появление КОНКРЕТНЫХ строк; в архив, если про качество перевода.
- `api`, `positive`, `negative`, `validation`, `boundary`, `rbac`, `capability`, `tenancy`,
  `lifecycle`, `idempotency`, `concurrency`, `state`, `navigation`, `session`, `security` — почти
  всегда АВТОМАТИЗИРУЕМО.

## Что делать с ⚠-кейсами (подозрение на баг / DRIFT)
- Если ожидаемое поведение детерминированно проверяемо (напр. «форма несовпадения пароля →
  сохранение заблокировано, диалог открыт») — ОСТАВИТЬ как автоматизируемое (это регрессионная
  проверка текущего поведения).
- Если ⚠ про визуал/цвет/перевод — в архив.
