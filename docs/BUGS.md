# Manzil — баги/дефекты, найденные автотестами

Открытые дефекты, обнаруженные UAT-автоматизацией. Каждый кейс, который из-за
бага нельзя пройти через UI, помечен `xfail` (с `run=False`) — суточный прогон
остаётся зелёным, а в директорском отчёте кейс показан как «Заблокирован (баг)».

## BUG-011 (P1) — ✅ ИСПРАВЛЕН (2026-07-03)

Билд приложения обновил экран адреса: лист адреса теперь = поиск + список
сохранённых + «Oʻz manzilingizni qoʻshish» → форма **Davlat** (Xitoy/Qirgʻiziston)
+ **поиск города** (выбор реального города → `cityId`) + свободный «Aniq manzil».
`POST /warehouse/locations` теперь идёт с `cityId` → 201, публикация проходит (201).
SK-05/06/07 разблокированы и зелёные (3/3 на свежем аккаунте). Ниже — исходное
описание бага для истории.

### (исходно) приложение склада не могло добавить адрес заявки

- **Где:** мобильное приложение склада `uz.logos.manzil.warehouse.staging`
  **версия 1.1.1-staging** (versionCode 3), экран «Создание заявки → Адрес
  отправления/назначения → Manzil qoʻshish».
- **Что происходит:** при нажатии «Qoʻshish» приложение шлёт
  `POST /api/v1/warehouse/locations` со свободным текстом города/страны
  (cityName + country, тело ~58 байт). Backend отвечает
  **`400 BAD_REQUEST` «Noto'g'ri so'rov»**.
- **Корень:** backend `/warehouse/locations` теперь принимает адрес **только по
  `cityId`** (UUID из справочника городов). Прежняя ветка «cityName + country»
  отключена — проверено напрямую по API: `{name, cityName, country, address}` →
  400, а `{name, cityId, address}` → 201. В форме приложения нет выбора города из
  справочника (только свободный ввод), поэтому получить `cityId` оно не может.
- **Эффект:** оператор склада **не может создать и опубликовать заявку через UI**.
- **Блокирует кейсы:** SK-05 (адрес отправления), SK-06 (адрес назначения),
  SK-07 (публикация).
- **Обходной путь в тестах:** заявки-предусловия для остальных кейсов
  поднимаются через API (`utils/api_seed.py`, шлёт `cityId`).
- **Что нужно от разработки:** в билде приложения заменить свободный ввод города
  на выбор из справочника и слать `cityId` в `POST /warehouse/locations`.

## BUG-012 (P1) — приложение склада не может отметить связь с водителем

- **Где:** то же приложение 1.1.1-staging, экран «Детали заявки (Ishda) →
  Haydovchi bilan aloqa → Ha, gaplashdik».
- **Что происходит:** приложение шлёт
  `POST /api/v1/warehouse/orders/{id}/communication` с телом ~16 байт
  (предположительно `{"status":"YES"}`). Backend отвечает
  **`400 BAD_REQUEST` «Noto'g'ri so'rov»**; статус связи остаётся
  «Aloqa talab qilinadi».
- **Корень:** backend ждёт enum `status=CONFIRMED` (так делает рабочий
  `api_seed`), приложение шлёт другое значение/поле.
- **Эффект:** нельзя отметить связь с водителем; кнопка «Yuk joʻnatildi»
  (отправить груз) остаётся неактивной — груз не отправить через UI.
- **Блокирует кейсы:** SK-12 (отметка связи), SK-13 (отправка груза).
- **Что нужно от разработки:** привести тело запроса communication к контракту
  backend (`status=CONFIRMED` / `NOT_REACHED`).

## BUG-013 (изменение UI, не дефект) — редизайн справочника городов ломает веб-формы

- **Где:** веб супер-админ, страница «Города» (`/super-admin/cities`) и форма
  добавления склада у грузоотправителя (`/shipper/warehouses`).
- **Что произошло:** на staging (деплой 2026-06-30) страница «Города»
  переработана в глобальный справочник с фильтром **Страна / Уровень / Путь /
  Пиньинь**; отдельный раздел «Страны». Кнопки «Добавить город» на странице
  больше нет — логика ручного добавления города меняется. Выбор города в форме
  склада использует новый справочник, структура комбобоксов изменилась
  (`get_by_role("option")` пуст → клик по опции таймаутит).
- **Данные:** справочник НЕ пустой (API отдаёт 3 страны и города Beijing/Tashkent),
  т.е. это не потеря данных и не сеть — именно редизайн UI.
- **Связь:** тот же деплой, что дал BUG-011/012 в приложении склада.
- **Эффект на автотесты:** SA-16 (добавление города), AD-14 (добавление склада),
  AD-15 (редактирование/удаление склада) не проходят на текущем UI.
- **Решение:** ПРИОСТАНОВЛЕНО (по решению заказчика — логика добавления городов
  ещё меняется). Кейсы помечены `xfail(run=False)`; в отчёте — «Заблокирован».
  Обновить POM (`pages/super_admin/dictionaries_page.py`,
  `pages/shipper/warehouses_page.py`) после стабилизации UI и снять xfail.

## BUG-014 (изменение UI) — действия жизненного цикла заказа переработаны

- **Где:** веб, детальная страница заказа у грузоотправителя (`/shipper/orders/{id}`)
  и оператора склада (`/shipper/storeroom/{id}`).
- **Что произошло:** в редизайне (деплой 2026-07-02, миграция на MUI DataGrid)
  действия над заказом — **Отмена**, **Связь с водителем**, **Повторная
  публикация** — больше не отображаются как кнопки/⋮-меню ни в строке списка
  (у строки заказа 0 кнопок), ни на детальной странице (только «Назад» + номер).
  На детали оператора есть текст «Связь», но не как кликабельная кнопка.
- **Эффект на автотесты:** AD-18 (отмена), MN-06 (связь), MN-08 (отмена),
  MN-09 (повторная публикация) не проходят — action-элементы не находятся.
- **Решение:** ПРИОСТАНОВЛЕНО (UI действий заказа в процессе переработки).
  Кейсы помечены `xfail(run=False)`; в отчёте — «Заблокирован». Обновить
  `pages/shipper/orders_page.py` / `storeroom_page.py` / `communication_page.py`
  когда action-UI заказа стабилизируется.

## Веб-редизайн (деплой 2026-07-02) — что уже адаптировано в POM

Списки мигрировали на **MUI DataGrid**; POM обновлён и снова зелёный:
- readiness-локатор `[role="grid"], table` вместо `role="table"`;
- поиск — под кнопкой **«Фильтры»** (`filter_search` / `filter_search_panel`);
- действия строки — **⋮-меню** и инлайн-иконки открываются клавишей **Enter**
  (`open_row_menu` / `activate`) — обычный click глотается гридом в headless;
- клик по строке-карточке — после **Escape** (закрыть Popper-панель фильтров).

Итог: SA 17/17, TK 14/14, AD/MN — кроме заблокированных выше — зелёные.
