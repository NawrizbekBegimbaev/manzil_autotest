BUG-001: Регистрация с дублирующимся email возвращает 204 вместо 409
================================================================================

Severity:           Major
Priority:           P1
Компонент:          Backend (auth-module/suppliers — отсутствует уникальность
                    email в рамках одного flow)

Описание:
    Повторная регистрация Supplier Admin с тем же email (но другим phone)
    возвращает 204 No Content вместо ожидаемого 409 Conflict.

    Странность: в текущем dev backend закрыты соседние uniqueness-проверки —
    дубль email cross-flow (supplier→TK) даёт 409, дубль phone в /suppliers
    даёт 409, дубль TIN cross-flow даёт 409. А вот этот один сценарий —
    дубль email в одном /suppliers с другим phone — всё ещё 204.

    По swagger-контракту 409 описан явно:
    "Email already registered or TIN already in use"

Шаги воспроизведения:
    1. POST /api/v1/auth/web/registrations/suppliers
       {"email":"dup@manziltest.uz", "tin":"200111222333",
        "phone":"+998900000010", ...} → 204
    2. POST /api/v1/auth/web/registrations/suppliers
       {"email":"dup@manziltest.uz", "tin":"200111222444",
        "phone":"+998900000011", ...}

Ожидаемый: Шаг 2 → 409 (Email уже зарегистрирован)
Фактический: Шаг 2 → 204 No Content (re-verified 2026-05-05)

Доказательство:
    - tests/auth/test_web_register_supplier.py::
        test_register_supplier_with_duplicate_email_returns_409
    - /tmp/bug_probe2.py (BUG-004 v2)

Возможные интерпретации:
    (а) БАГ: backend забыл проверить уникальность только для этой комбинации.
    (б) ФИЧА: повторный POST триггерит resend OTP (идемпотентность).
        Тогда swagger описывает несуществующий 409 — нужно обновить.

Рекомендация:
    Backend lead должен решить:
        1. Если "идемпотентный resend" — задокументировать в swagger,
           убрать 409 из responses.
        2. Если уникальность нужна — добавить SELECT по email перед INSERT,
           вернуть 409 на дубль (как уже сделано для phone и cross-flow email).

BUG-003: UI принимает ИНН только 8–18 символов, API — 1–18 (контракт-дрифт)
================================================================================

Severity:           Major (UI блокирует валидные с точки зрения API данные)
Priority:           P1
Компонент:          Frontend (форма регистрации Supplier/TK)

Описание:
    На /auth/register/supplier и /auth/register/tk форма блокирует submit
    при длине ИНН < 8.

    Бэкенд по swagger принимает паттерн `^[0-9]{1,18}$` — т.е. от 1 цифры.
    Расхождение: пользователь, у которого валидный по API ИНН 5–7 цифр
    (теоретический edge — в РУз стандарт 9, но другие страны могут
    отличаться), не сможет завершить регистрацию через UI.

    Re-recon 2026-05-05: текст ошибки изменён («Только цифры» вместо
    «ИНН от 8 до 18 символов»), но drift сохранился — UI всё ещё
    отклоняет 5-цифр ИНН.

Шаги:
    1. Открыть https://dev-manzil.greatmall.uz/auth/register/supplier
    2. В поле «ИНН / аналог» ввести `12345`
    3. Заполнить остальные поля валидно
    4. Нажать «Зарегистрироваться»

Ожидание:  submit принят, переход на экран OTP (поведение API).
Факт:      Inline-ошибка «Только цифры» (на 5 цифрах!), кнопка не
           отправляет запрос на бэк.

Доказательство:
    - web_ui/supplier/auth/test_pre_otp_register.py
    - Playwright probe 2026-05-05: TIN=12345 → form blocks submit.

Рекомендация:
    Согласовать диапазон с командой бэка:
    - расширить UI-правило до 1–18 (соответствует swagger), или
    - сузить swagger-регулярку до `^[0-9]{8,18}$` и обновить контракт.
    Сейчас два слоя противоречат друг другу.

BUG-005: MZL-номера заявок не уникальны глобально между компаниями
================================================================================

Severity:           Minor (UX неоднозначность)
Priority:           P3
Компонент:          Backend (нумерация заявок)

Описание:
    MZL-номер (MZL-NNNN) генерируется per-company (счётчик у каждого
    поставщика начинается с 0001). В TK-ленте /feed одновременно
    видны заявки от разных поставщиков, что может приводить к
    нескольким одновременно видимым «MZL-0012» от разных компаний.

    Не критично (заявки в БД идентифицируются UUID), но в UI
    создаёт неоднозначность — пользователь не может сослаться на
    «MZL-0012» без указания компании.

Доказательство:
    - web_ui/e2e/test_tender_flow_cross_role.py — пришлось искать
      созданную заявку по уникальному cargo_type, а не MZL-номеру.
    - В live-данных на dev уже видны >1 строки «MZL-0001»,
      «MZL-0002», «MZL-0003» от разных suppliers.

Рекомендация:
    Один из вариантов:
    1. Глобальный счётчик MZL-номеров (просто, но «теряет красоту» seq).
    2. Префикс компании в номере: «TQ-MZL-0012» / «AC-MZL-0012» где
       TQ/AC — короткий код компании.
    3. Скрыть MZL в TK-ленте, использовать только UUID-короткий.

BUG-006: На «В работе» заявке UI не показывает action-кнопки матрицы
================================================================================

Severity:           Major (заблокированный workflow)
Priority:           P1
Компонент:          Frontend (страница /orders/{id})

Описание:
    Страница заявки в статусе «В работе» по матрице должна показывать
    у ADMIN и MANAGER:
    - кнопку «Завершить» (перевод в «Завершена»)
    - кнопку «Отменить»
    - на каждом оффере: кнопку «Заметка»
    - кнопку «Выбрать победителя» (если ещё не выбран)

    Реальность (наблюдалось в MCP-сессии 2026-05-03):
    - У ADMIN на «В работе»: только «Назад». Никаких других кнопок.
    - У MANAGER на «В работе»: «Назад» + «Заметка» (на оффере).
      Никаких «Завершить»/«Отменить»/«Выбрать победителя».

    То есть весь activeFlow тендера (после выбора победителя)
    выполним только через прямые curl-вызовы API. Это критический
    UX-блокер: ни один пользователь не сможет завершить заявку
    через UI.

    Re-recon 2026-05-05: probe не получилось (нет «В работе» заявки
    в текущих данных), но статус не помечен как закрытый — нужна
    повторная UI-рекон при появлении такой заявки.

Доказательство:
    - web_ui/supplier/orders/test_order_detail.py — тесты на статус-
      badge и presence/absence кнопок видят только «Назад».
    - API endpoints (`/orders/{id}/complete`, `/cancel`, `/select`,
      `/offers/{id}/note`) при этом работают и покрыты API-тестами.

Рекомендация:
    Добавить в /orders/{id} рендер action-buttons по статусу + role:
    - «Активна» + ADMIN/MANAGER → «Отменить»
    - «В работе» + ADMIN/MANAGER → «Завершить» + «Отменить»
    - «Активна» с офферами + ADMIN/MANAGER → «Выбрать победителя»
    - DRAFT + own DISPATCHER → «Опубликовать», «Редактировать»
    - На каждом оффере, ADMIN+MANAGER → «Заметка»

    После починки добавить ~10 UI-тестов на эти flow.

BUG-007: TK /offers ломается на «404 Заявка не найдена», если есть оффер на
         удалённую/отменённую заявку
================================================================================

Severity:           Major (страница недоступна)
Priority:           P1
Компонент:          Frontend (TK /offers + backend offer-listing)

Описание:
    После прогонов cross-role e2e тестов остаются закрытые (cancelled)
    заявки, к которым ранее были приcлeлы офферы от TK. На странице
    /offers (history of TK's outgoing offers) фронт пытается отрендерить
    карточку оффера, фетчит данные связанной заявки, получает 404 и
    показывает страницу «Ошибка (404). Заявка не найдена. [Повторить]
    [На главную]» вместо списка офферов.

    То есть один «битый» оффер ломает ВСЮ страницу /offers — нет fallback
    «пропустить эту строку» или «показать как удалённую».

    NB: на 2026-05-05 проверка precondition заблокирована — TK_ADMIN
    JWT отвергается на /api/v1/my-offers (см. BUG-008).

Шаги воспроизведения (когда BUG-008 исправлен):
    1. TK подаёт оффер на заявку поставщика
    2. Поставщик отменяет заявку (status=CANCELLED)
    3. TK открывает /offers
    4. Страница показывает 404, не таблицу

Доказательство:
    - GET /api/v1/my-offers → 200 с массивом офферов (включая со
      SELECTED-статусом) — was working before BUG-008
    - UI на /offers рендерит «Ошибка (404). Заявка не найдена» вместо
      таблицы.

Рекомендация:
    Frontend: не падать на 404 связанной заявки — показывать строку с
    плейсхолдером «Заявка удалена/отменена» (offerData всё ещё валидно).
    Backend: либо включать в /my-offers денормализованные поля заявки,
    либо явно фильтровать офферы на отменённые заявки на бэке.

BUG-008: TK_ADMIN JWT отвергается с 401 на /me, /my-offers, /feed (NEW)
================================================================================

Severity:           Critical (TK не может пользоваться приложением)
Priority:           P0
Компонент:          Backend (Spring Security / JWT validation для TK ролей)

Описание:
    POST /api/v1/auth/web/login для TK админа возвращает 200 с валидным JWT
    (iss=manzil-dev, realm_access.roles=['TK_ADMIN']). Однако:
        GET /api/v1/me           → 401 «Требуется авторизация»
        GET /api/v1/my-offers    → 401
        GET /api/v1/feed         → 401
        GET /api/v1/orders       → 403 (ожидаемо — TK не должен видеть)
    SUPPLIER_ADMIN с тем же realm/issuer на /me → 200.

    То есть TK login видимо проходит (storage_state сохраняется), но
    любая страница приложения для TK сломана — каждый запрос к API
    возвращает 401.

Шаги воспроизведения:
    POST /api/v1/auth/web/login {"email": "<tk_admin>", "password": "..."}
    GET  /api/v1/me с Authorization: Bearer <accessToken>

Ожидаемый: 200 + UserResponse с ролью TK_ADMIN.
Фактический: 401 «Требуется авторизация».

Доказательство:
    - Прямая проба 2026-05-05: оба токена (TK + SUPPLIER_ADMIN) валидны
      по JWT-формату, оба issued тем же realm `manzil-dev`. /me для
      SUPPLIER → 200, для TK → 401.
    - JWT payload TK: realm_access.roles=['TK_ADMIN', 'default-roles-manzil',
      'offline_access', 'uma_authorization'].

Влияние:
    1. TK не может загрузить ни одну страницу приложения.
    2. Блокирует verifying BUG-007 (orphan offer на 404 заявку) — основной
       precondition недоступен.
    3. Регрессия: до 2026-04-30 TK login был рабочим (см. tests/auth/
       test_web_login.py — тест logged-in TK).

Рекомендация:
    1. Проверить Spring Security конфигурацию: какие realm-роли
       разрешены на /api/v1/me, /my-offers, /feed.
    2. Если конфиг whitelisting'ит только SUPPLIER_*-роли — добавить
       TK_ADMIN, TK_DRIVER в список разрешённых.
    3. Добавить интеграционный тест: TK_ADMIN JWT → /me → 200.

BUG-009: Регистрация позволяет создать 2 аккаунта на один и тот же номер телефона
================================================================================

Severity:           Major (нарушение бизнес-инварианта уникальности)
Priority:           P1
Компонент:          Backend (auth-module — отсутствует/сломана уникальность
                    phone в registration flow)
Обнаружено:         2026-05-06 (manual repro)

Описание:
    Backend принимает второй POST на регистрацию с тем же phone и создаёт
    второй аккаунт вместо того чтобы вернуть 409 Conflict. На один номер
    телефона можно зарегистрировать 2 разных аккаунта — что нарушает
    бизнес-инвариант (телефон должен однозначно идентифицировать
    пользователя/компанию для OTP, recovery, mobile login).

    NB: BUG-001 ранее упоминал, что «дубль phone в /suppliers даёт 409».
    Сейчас это не подтверждается — либо регрессия в /suppliers, либо
    проверка отсутствует в смежном flow (TK / mobile/driver / web-invite).
    Нужно прогнать дубль-phone репро по всем flow:
        - POST /api/v1/auth/web/registrations/suppliers
        - POST /api/v1/auth/web/registrations/trucking-companies
        - POST /api/v1/auth/mobile/registrations/drivers
        - POST /api/v1/employees (invite — по идее phone не обязателен,
          но проверить если поле принимается)

    По swagger-контракту 409 «Phone already registered» должен возвращаться
    при дубле phone (аналогично email/TIN — те уже enforce'ятся).

Шаги воспроизведения:
    1. POST /api/v1/auth/web/registrations/suppliers
       {"email":"a@manziltest.uz", "tin":"200111000001",
        "phone":"+998900000099", ...} → 204
    2. POST /api/v1/auth/web/registrations/suppliers
       {"email":"b@manziltest.uz", "tin":"200111000002",
        "phone":"+998900000099", ...}   ← тот же phone, другой email/TIN

Ожидаемый: Шаг 2 → 409 Conflict
           ProblemDetail.title="Phone already registered"
Фактический: Шаг 2 → 204 No Content (создаётся второй аккаунт на тот же
             номер, оба получают OTP / могут довести регистрацию до конца).

Влияние:
    1. Mobile login по phone становится неоднозначным — какой аккаунт
       аутентифицировать?
    2. SMS/Telegram OTP на recovery/verify уходит на чужой номер (если
       один и тот же phone у двух пользователей — кто получает код?).
    3. Account takeover risk: злоумышленник регистрирует второй аккаунт
       на телефон жертвы, перехватывает OTP и получает доступ.
    4. Нарушает обещанный swagger-контракт (409 для phone duplicates).

Доказательство:
    - manual repro 2026-05-06 (см. описание шагов выше)
    - TODO: добавить тест tests/auth/test_web_register_supplier.py::
        test_register_supplier_with_duplicate_phone_returns_409
      (сейчас, вероятно, отсутствует или падает — нужно проверить)

Рекомендация:
    1. Добавить (или починить) UNIQUE-constraint / SELECT-проверку по phone
       в registration-сервисе для всех flow (suppliers, trucking-companies,
       drivers).
    2. Возвращать 409 Conflict с ProblemDetail.detail указывающим на phone.
    3. Решить, нормализовать ли phone до E.164 ДО проверки (иначе
       «+998 90 000 00 99» и «+998900000099» считаются разными).
    4. Добавить регрессионный тест на каждый из перечисленных flow.

Связанные баги:
    - BUG-001 (дубль email в /suppliers → 204 вместо 409) — тот же класс
      проблемы (отсутствие uniqueness в registration), но для email.
